## Executive Summary

The code is in good mechanical health: typecheck is clean, 340 unit tests and the 14-case Docker suite pass with no flakes, `npm audit` reports nothing, no dependency is outdated, and the sandbox's container flags, argument handling and path confinement were checked and found sound. The inspection's main finding is a documentation claim the design cannot support: the README says the agent never sees `{slug}__{NAME}` values, but the agent can read them through tools it already has, and that was demonstrated on a throwaway container. Behind it sit three related design gaps (who may read a project's variables, what a slug identifies, who owns a sandbox) that belong in one design sortie, plus a set of bounded fixes: no CI gate on a `main` that every `npx` consumer builds, install failure paths that leave a sandbox online, and local state that is never reconciled at startup.

**Details:**

- **1a / 1b — the agent can read a project's variables.** `README.md:235` says "The agent never sees the values, and nothing is stored". Three paths contradict it, none needing a hostile repository:
  - `connect_mcp_server` accepts any argv whose first element has no whitespace or NUL (`src/server.ts:838-867`), so `["sh","-c","env >&2; exit 1"]` is accepted. `Installer.launchSpec` (`src/install/installer.ts:141-143`) adds every `{slug}__*` value to every launch whatever its origin, including client-registered ones (`connectMcp`, 357-362). A failed handshake puts `stderr.slice(-1500)` into the thrown error (`src/proxy/mcp-proxy.ts:152-163`), which `callTool` returns as `Error: …` (`src/server.ts:440-443`). Nothing in `src/` compares output against the values. *Read by the Security Reviewer and independently by the Architect; not run end to end.*
  - `sandbox_exec` runs as the same user in the same PID namespace as a running proxied server (`docker exec` never passes `--user`), so it can read `/proc/<pid>/environ`. *Ran*: on a throwaway container with the product's flags (`--network none`, cap-drop ALL plus the six capabilities, `no-new-privileges`, `--init`; image `alpine/git:latest`, not a project image), a process was started with `docker exec -d --env-file` as `dockerConnector` does, and a second plain `docker exec` read its environment and got the dummy value. The container and env file were removed.
  - `sandbox_write_file` can overwrite the code an auto-detected launch runs. *Read.*
  - The README's limitations section (lines ~358-370) already says that any code in the sandbox can read a running server's variables through `/proc/<pid>/environ` and that the Docker client inherits the whole environment. Sortie 03 accepted those limits. What is undocumented, and contradicted by line 235, is that the **agent** is among the readers.
  - The Security Reviewer first proposed handing variables only to operator-approved launches; the Architect showed that cannot hold against an agent with exec or write on the same project, and the reviewer withdrew it. Options for 1b, as the reviewer framed them: (1) the agent is not an adversary — say so in the README and charter, and do not set variables for a project whose output is not trusted; (2) disable `sandbox_exec`, `sandbox_write_file` and `connect_mcp_server` for projects that have variables; (3) a separate uid and PID namespace for the proxied server; (4) a separate container for it. The reviewer recommends 1 now, 2 if a real boundary is wanted; 3 and 4 are redesigns.
  - A sentence that is true today: variables set as `<slug>__<NAME>` are handed to every MCP server of that project, and anything with `sandbox_exec`, `sandbox_write_file` or `connect_mcp_server` on the same project, including the agent, can read them directly or by replacing the server's code.
  - Severity calibration: the Architect rates 1a Critical because operators set real API keys on the strength of that line, and notes the operator may reasonably read it as Action Required given the limitations section; the vehicle and timing are the same either way.
- **2 — slug identity.** `makeSlug` (`src/toolgen/naming.ts:24`) uses the repository name, not the owner or repository id. Uninstalling a project and installing another repository of the same name gives the same slug and its variables; `install_project` takes `network: true` from the caller, so discovery would run the new repository's code with the variables and the network on. The code does nothing beyond listing variable names after delivery (`installer.ts:130-134`, `src/proxy/host-env.ts:26-41`). *Read.* Prefix ambiguity is the low end of the same problem: if slug `a__b` is not registered, `a__b__TOKEN` goes to project `a` as `b__TOKEN`. Tool calls are never misrouted, because `findGenerated` requires membership. Squawk 0008 (slugs containing `__`) has the same root.
- **3 — sandbox ownership.** The check covers `removeContainer` and `destroy` only, and tests the generic label `mcp-everything=1`. `exec`, `ensureRunning`/`docker start` and the secret hand-off act on whatever container has the name `<prefix><slug>` (`src/sandbox/docker.ts:~316-345, 380-400`). The `mcp-everything.project` label is written and never read. *Read.* *Ran*: `docker ps -a` shows `mcpe-cowsay` and `mcpe-ha_googlehome`, which are not in the inspected registry (only `gron` and `rea` are). The cause was not established; the sortie 03 debrief records that the operator's two clients keep separate data directories under one name prefix, which would explain it (inferred). The integration tests' prefix `mcpe-it-<pid>-` also begins with the product default, which would matter to any future prefix-based sweep.
- **3a** — `src/config.ts:~97`: a typo in the prefix puts a second registry back on the shared default without a word. *Read.*
- **4 — install failure paths** (also Categories 2 and 10). The container is created on `bridge` and `setNetwork(wantNetwork)` runs only after the recipe returns (`installer.ts:~231`). If an earlier step throws, the `catch` keeps the sandbox, registered as `failed`, still on the network; if the server process dies mid-install the record stays `installing` with the sandbox online. `sandbox_exec` then runs in it, and the failure advice ("enable `set_project_network`") implies the network is off. `App.shutdown` closes proxied servers only, and the handler in `src/index.ts:13-23` has no timeout and can be re-entered by a second signal. `disconnectMcp` (`installer.ts:370-389`) skips `requireSandbox` and ends with `registry.put` instead of `finish()`; because discovery swallows exec errors, on a missing sandbox it would store a record with its commands emptied (effect inferred). None of the failure branches has a unit test: the rollback with `sandboxCreated=false` (289-296), the timeout path (277-285), `uninstall` (680). *Read.* The reviewers called the network and `disconnectMcp` parts squawk-sized; the Architect disagreed because both change network or registry lifecycle, so they go in a flight.
- **5 — secret hand-off tests.** The assertion at `test/server.test.ts:~730` records only `Docker.exec` calls, while proxied launches go through the connector, so it cannot fail for launch argv. The real `dockerConnector` (`--env-file`, mode 0600, value not in argv) is exercised only by the Docker-gated suite, which checks neither file mode nor argv. An env file left by a crash between write and cleanup stays in `<dataDir>/tmp` (0700 directory, 0600 file); nothing sweeps it at startup. *Read.* This should land before the design sortie reworks the launch path.
- **10** — every `MCPE_WARN …` line a build prints becomes a warning: 300 characters each, count unbounded, from up to 4 MB of output. `describe()` prints all of them, they are stored in `registry.json`, and they are not marked as untrusted (`installer.ts:~214-224`). *Read.*
- **23 — checked and sound.** *Ran*: `docker inspect` on four live sandboxes shows not privileged, cap-drop ALL plus six capabilities, `no-new-privileges`, memory 4g, pids 1024, only the project volume mounted, no Docker socket, no host mounts, default seccomp and AppArmor, no host network; stopped and restarted sandboxes keep zero attached networks; `parseHelp` on 100 KB adversarial inputs takes under 5 ms; `npm audit` reports 0 vulnerabilities; no secrets in source, tests or any of the 24 commits. *Read*: no shell on the host anywhere (`spawn` with an argv array); git ref and clone URL validation; file tools confined to `/workspace`; forge tokens sent only to their own API hosts; env file removed in `finally`, values never in argv or the registry; one project's tools cannot reach another's container; no `curl | sh` in recipes.
